## 3. F.17 / G.1 — batch truncation (KNOWN behaviour, not "long batches fixed")

Code: `keybd_shift.cpp:428–456`. The output-key loop is still bounded on the running total
(`n < MAX_KEYEVENT_INPUTS - MAX_KEYEVENT_INPUTS_MODIFIERS`, i.e. 248), so with a full release half
only 240 output keys fit and what is sent is a **prefix** (tail dropped). New: when
`outputKeysCopied < nInputs`, `*pOutputKeysTruncated = nInputs - outputKeysCopied` (against the
clamped ≤256 nInputs) and `pfnDiagnostic(BatchOutputTruncated, 0)` is called **once per batch**,
vk = 0; a fitting batch writes 0 and reports nothing. Production thunk logs it via
`SendDebugMessageFormat` (`serialkeyeventserver.cpp:123–130`).

Tests that pin it — all PASS on x64 and x86:

- `MODIFIER_DIAGNOSTIC.ATruncatedBatchIsNamedInTheDiagnosticAndCountsItsDrop` (tests.cpp:2052) —
  6 modifiers held + 256 output keys → n = 256, truncated = 16, `BatchOutputTruncated` count = 1, vk 0.
- `MODIFIER_DIAGNOSTIC.ABatchThatFitsReportsNoTruncation` (tests.cpp:2080) — 1 key → truncated = 0,
  no diagnostic.
- `PREPARE_INJECTED_INPUT_BATCH.WorstCaseBatchFillsTheBufferToItsLastSlotAndNotOneFurther`
  (tests.cpp:799) — 8 + 240 + 8 = 256, exactly 240 'A' output keys, guard slots untouched.
- `PREPARE_INJECTED_INPUT_BATCH.NeverWritesPastTheBufferWhenTheSharedBufferOverflows` (tests.cpp:751)
  — nInputs = 306 clamped, n = 256.

Recorded as KNOWN: long batches (>240 output keys with a full release half; >248 with none) are
still truncated to a prefix. Not tested on a real keyboard (none in scope produces >240 keys).

Observation for the reviewer (not a failure): the production caller
(`serialkeyeventserver.cpp:768–770`) does **not** pass `pOutputKeysTruncated` (defaults to NULL), so
in production the drop is visible only as the debug/ETW line, not as a count the server acts on. The
out-param is exercised only by the tests. This matches "a diagnostic and/or a caller-visible signal",
but the caller-visible half is currently unused.

### Does the gate need keyman64.dll swapped for x64 Notepad? — No.

The serializer server, the LL hook and the modifier cache (where the fix lives) are compiled only
into the 32-bit engine (`serialkeyeventserver.cpp:11`, `k32_lowlevelkeyboardhook.cpp:31`,
`#ifndef _WIN64`) and run inside 32-bit keyman.exe. A 64-bit app's keyman64.dll is only a client: it
writes into the shared mapping `KeymanEngine_KeyEvent_FileMapping` and the 32-bit server assembles and
injects the batch (README "Host bitness", lines 122–141). The PR does not change the client
(`serialkeyeventclient.cpp` untouched) or the shared struct layout, so stock keyman64.dll + branch
keyman32.dll is wire-compatible. deploy-8064.ps1 swaps keyman32.dll only, by design, and the
2026-08-31 evidence pair (`gate-pass-fixed-19.0.277.txt`: "One variable changed: keyman32.dll")
passed the gate on 64-bit Notepad that way. Caveat to state in the report: keyman64.dll-side code in
this PR (e.g. new helpers in keybd_shift.cpp compiled into both) is not exercised by the fixed arm;
the x64 unit suite is its only coverage.
