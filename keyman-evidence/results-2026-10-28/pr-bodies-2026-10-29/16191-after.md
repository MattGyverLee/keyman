## Summary

Third and smallest of the Delphi 12 CE workflow PRs. It makes `delphi_msbuild` fail loudly in the two situations where a CE build used to "succeed" with no output:

1. **CE without `KEYMAN_DELPHI_CE=1`.** A `dcc32.exe` probe detects Community Edition and aborts with a message pointing at the CE guide.
2. **A CE prompt answered without an IDE build.** After the prompt, the project's output must have been written since the prompt was shown, or the build dies.

## The problem

If a contributor is on Delphi 12 CE and forgets to `export KEYMAN_DELPHI_CE=1` in their shell (easy to do — SETX only affects new shells), `delphi_msbuild` falls through to `msbuild.exe`. On CE, msbuild reports:

```
Build succeeded.
    0 Warning(s)
    0 Error(s)

Time Elapsed 00:00:01.23
```

...and produces **no output**. Downstream `cp`, `mv`, `mt.exe`, `sentrytool_delphiprep` steps then fail with "file not found" errors pointing at paths Delphi never wrote to. Diagnosing this from the symptom takes considerable time — you chase the missing file assuming Delphi's build worked, when really Delphi never ran.

The CE prompt in #16044 had the same weakness in another form: pressing Enter without building, or stdin closing (a piped or non-interactive run), returned success and the build carried on with stale or missing output.

Discovered while running the CE workflow walkthrough for #16044; every "Delphi silently succeeded but no output" issue I hit traced back to one of these.

## What the change does

All in `resources/build/win/environment.inc.sh`:

- **`_probe_delphi_ce`**, cached per shell. CE's `dcc32.exe` is a 23KB stub that prints `This version of the product does not support command line compiling.` and exits non-zero; Pro/Enterprise's `dcc32.exe` is the real compiler. The probe runs once per shell and sets `_KEYMAN_DELPHI_IS_CE=1` if the marker string is present. If the probe detects CE and `KEYMAN_DELPHI_CE != 1`, `builder_die` with a message pointing at `docs/build/windows-delphi-ce.md`.
- **Fail-loudly prompt.** A marker file is created just before the prompt is shown. After the prompt (Enter, or EOF), the output at the project's real output path must be newer than that marker; otherwise `builder_die` says the project was not built in the IDE. Success is defined by the output, not by the keypress.

## CI impact

**None.** CI runs on Delphi 10.3 Pro. The probe hits Pro's real `dcc32.exe`, doesn't see the CE marker, and `delphi_msbuild` proceeds to msbuild normally. The prompt code only runs with `KEYMAN_DELPHI_CE=1`. The added overhead is one dcc32 spawn per build.sh invocation — trivial.

## Verified

On Delphi 12 Athens CE (2026-10-28): the guard fires both ways (CE without the variable dies; Pro path untouched by inspection), and the prompt dies on stdin closed and on Enter without building. Real IDE runs: prompt, build, Enter is accepted every time, with each package `.bpl` accepted at its real path.
