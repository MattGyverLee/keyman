## Fix 1 — X1 + freshness (#16044 code, #16191 post-prompt check)

### What changed

`resources/build/win/environment.inc.sh` (line numbers at fix2/16191):
- **:112–119, session marker (#16044, b6c78141cd).** Under `KEYMAN_DELPHI_CE=1` only, sourcing creates `${_builder_deps_built}.delphi-ce-session` once, if it does not exist yet. `_builder_deps_built` is builder's per-run temp file. builder_parse creates it fresh (mktemp) for every top-level run and exports it to child and dependency builds (`builder.inc.sh` ~1738, verified at ~1780). So every nested build.sh in one top-level run shares one marker, and a new top-level run always gets a new one. If no builder session exists, the fallback is a per-process mktemp. The marker is not exported itself, so it cannot leak across runs through the environment. It leaves one empty temp file per CE run, by design (comment says so).
- **:127–157, `_delphi_ce_output_files` (#16044).** Reads the real output folder from the `.dproj`: `DCC_BplOutput` for a `.dpk` (→ `.bpl`), and `DCC_ExeOutput` otherwise (→ `.exe`/`.dll`). It expands `$(Platform)`/`$(Config)`, resolves against the `.dproj`'s own folder (which handles `packages/CEF4Delphi.dproj` and the `pushd packages` / `pushd components` callers), and falls back to `bin/<Platform>/<Config>` when there is no `DCC_ExeOutput`. Config now follows `TARGET_PATH` instead of a hard-coded `Debug`, and the prompt prints it.
  Resolution was checked against every package step:
  - common_components → `common/windows/lib/common_components.bpl`
  - CEF4Delphi → `common/windows/lib/CEF4Delphi.bpl`
  - Jcl/JclVcl/JvCore/JvCoreDesign/JvDocking/JvDockingDesign → `developer/lib/*.bpl`
  - developer_components → `developer/lib/`
  - mbColorLibD10 → `developer/lib/`

  These are the same `/developer/lib/...` and `/common/windows/lib/...` paths each package's `builder_describe_outputs` and `devtools -ip` use.
- **:160, `_delphi_ce_output_newer_than` (#16044).** Returns true when any expected output is `-nt` a given marker.
- **:200–206, auto-skip (#16044).** Skips only when the output is newer than the session marker. Output from before this top-level run is never trusted, whatever the `.dpr`/`.pas` mtimes say. The `.dpr` comparison is gone.
- **:209–235, post-prompt check (#16191, 7476a9e54c, now 65a6384342).** `prompt_marker=$(mktemp)` is recorded **before** the prompt is printed. After Enter or EOF, success requires output at the real path that is newer than that prompt marker. Otherwise it fails with `builder_die`, and the message lists the paths checked. stdin EOF still prints the "no Enter received" warning and then dies.
- **:238–244, CE-unset guard: unchanged** (byte-identical to 331b0b3015).

Rebase conflict in 331b0b3015 → c53fd9ecdb: the old post-prompt `_delphi_ce_output_fresh` call was resolved to the equivalent new call, which compares against the session marker. The new prompt-time messages come from #16044. 7476a9e54c then tightens the check to the prompt marker.

## Fix 2 — CE guide §5 + uiAccess (#16044, f4c4496a89, now 80d6bda850)

`docs/build/windows-delphi-ce.md` at fix2/16044:
- **§5 retitled "Running a dev keyman.exe (uiAccess)" (:288).** It states Microsoft's two documented checks: the signature must chain to the local machine Trusted Root store, and the binary must be in a secure location.
- **"Recommended: sign with the Keyman test certificates" (:308).** Steps:
  1. Generate the certs (§1).
  2. **Elevated, once**: `certutil -addstore Root KeymanTestCA-sha256.cer` and `... KeymanTestCA-sha1.cer`, into the LocalMachine Root store.
  3. `./build.sh build publish`. `publish` validates that `uiAccess="true"` is still in the linked manifest and signs `windows/bin/engine/keyman.exe` via `wrap-signcode` with the test pfx. symstore skips with a warning when `KEYMAN_SYMSTOREPATH` is unset; that was verified by reading `environment.inc.sh` `wrap-symstore`.
  4. Elevated `windows/src/engine/build.sh install`, which installs into `Program Files (x86)\Common Files\Keyman\Keyman Engine`, a secure location.

  The section also has a security note, with the removal commands.
- **"Last resort, local only: strip uiAccess" (:346).** Kept, but only as a clearly labelled last resort, and as the one-attribute edit to `manifest.in`. Decision: keep rather than drop. Reason: the signed route needs a machine-wide trusted root whose private key sits on disk, which some contributors will not or cannot accept. For UI-only work, the one-attribute strip is then the least-invasive fallback. The section says plainly that results from it say nothing about elevated-app behaviour, and that `publish` rejects that binary by design.
- **The inaccurate debug-manifest description is fixed.** The guide now says not to use `./build.sh debug-manifest` / `--debug-manifest` for this, because `debug-manifest.in` also:
  - drops `dpiAware`
  - drops the supportedOS GUIDs (Vista–10)
  - drops the Common-Controls v6 dependency
  - renames the assemblyIdentity

  The action restores `manifest.in`, so only `manifest.res` changes. The old text said it "copies debug-manifest.in over manifest.in".
- §1 (:48): the `-user` import is enough for signtool, not for uiAccess. Points to §5.
- Troubleshooting `error=8235` (:444): the cause now lists unsigned, untrusted-root, or non-secure-location.
- Also in this commit (same-layer factual fix): §4 now describes the same-run auto-skip and real output paths (:162), says Build All belongs at the first prompt (:223), and corrects ":181 insthelper not in the group". The #16044 groupproj fix puts it in the group.

### uiAccess cert-store finding

**Answer: yes — per Microsoft's documentation the test CA must be in the LocalMachine Root store, which needs admin. `certutil -user -addstore Root`, which is what `certificates/build.sh` does, is not sufficient.**

- Microsoft, archived WinSDK blog quoting the Vista UAC developer requirements: "The application must have a digital signature that can be verified using a digital certificate that chains up to a trusted root in the **local machine** Trusted Root Certification Authorities certificate store", and "must be installed in a local folder application directory that is writeable only by administrators, such as the Program Files directory". Its install steps import the cert via MMC → Computer account → Local Computer → Trusted Root, from an elevated prompt. https://learn.microsoft.com/en-us/archive/blogs/winsdk/setwindowhookex-api-with-wh_journalrecord-this-api-fails-with-access-denied-error-5
- Microsoft Learn, "User Account Control: Only elevate UIAccess applications that are installed in secure locations" (applies to Windows 10/11; default Enabled):
  - "digital signature that can be verified by using a digital certificate that is associated with the Trusted Root Certification Authorities store on the local device"
  - secure locations are `%ProgramFiles%` and its subdirectories, and `%WinDir%` and its subdirectories except the standard-user-writable ones
  - "Windows enforces a PKI signature check on any interactive application that requests running with a UIAccess integrity level, regardless of the state of this security setting"

  https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/user-account-control-only-elevate-uiaccess-applications-that-are-installed-in-secure-locations
- Microsoft Learn, UI Automation security overview: the app must be Authenticode-signed and installed in a secure location that requires a UAC prompt for access, e.g. Program Files. https://learn.microsoft.com/windows/win32/winauto/uiauto-securityoverview
- Wording note: the current policy page says "on the local device", which is less explicit than the archived "local machine ... store". No Microsoft page I found discusses the CurrentUser Root store for uiAccess. The claim that the AppInfo service (running as SYSTEM) performs the check, so it cannot see HKCU stores, is **UNVERIFIED**: no Microsoft source found.
- This machine, read-only check: `certutil -user -store Root` lists `Keyman Test CA` and `Keyman Test CA SHA1`. `certutil -store Root` (LocalMachine) lists neither. So the documented route needs one elevated `certutil -addstore Root` per CA here.
- **Not empirically tested.** Launching a test-signed keyman.exe was not possible during the injection test, and needs admin anyway. The 8235 seen earlier was with an **unsigned** binary, so it does not tell CurrentUser apart from LocalMachine. Empirical confirmation is owed: sign, install, and launch first with only the CurrentUser root, then with LocalMachine.
