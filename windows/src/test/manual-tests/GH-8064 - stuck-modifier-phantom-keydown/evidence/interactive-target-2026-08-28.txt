## The finding this run produced that was not being looked for

`ReconcileDoesNotRaceItsOwnInjectedRestorePress` did not terminate before this run. Phase 1 recorded
it hanging indefinitely on both architectures and had to exclude it by GTEST_FILTER to get a
baseline at all (T004, T005); a first attempt here ran 26 minutes and printed nothing. **It was
never wedged.** With per-iteration progress and an unbuffered stdout added, the cause is plain:

    SendInput cost, measured per EVENT IN THE BATCH, on this machine with Keyman running

        depth   1 event     x86  127548 us/event      x64   24183 us/event
        depth  33 events    x86  114057 us/event      x64   46667 us/event
        depth 201 events    x86  110106 us/event      x64  112906 us/event

That is on the order of **0.1 seconds per injected key event**, against the microseconds SendInput
costs with no hook chain. The test's original shape asked for 100 trials at each of three depths:
100 x 201 events x 0.11s is about six hours for the last depth alone. The "hang" was a linear
blow-up in batch depth, not a deadlock, and the settle-spin counters confirm it -- `at-limit=0` at
every depth, so the injected releases were all landing promptly; nothing was waiting on anything.

The cost is a property of the low level hook chain on this machine, not of `SendInput`, and it is
the same round trip the engine pays for every batch it injects. Two things follow, and neither is
in scope here:

  - it is worth knowing that an injected modifier batch of any depth is not free on a machine with
    hooks installed, and
  - the x86/x64 spread at depth 1 (128ms vs 24ms) is five-fold in the same session, so the figure
    is load-dependent, not architecture-dependent. Treat any single number here as an upper bound
    on a loaded machine.

The test now gives each depth a wall-clock budget (100s) and reports the trial count it achieved,
failing only if a depth cannot manage three trials. A budget-bound N is an honest statistical
statement; a fixed N nobody can reach is a test that never runs, and a hang is not a statement at
all. The trial counts above -- 100, 63, 5 on x64 and 100, 26, 5 on x86 -- are the real strength of
the measurement, and they are printed rather than implied.

In all 118 (x86) and 168 (x64) trials that ran: **races=0, staleReads=0**. `SendInput` did not
return before the injected press was visible to `GetAsyncKeyState`, at every depth reached. The
property `ReconcileModifierCache` depends on still holds on this machine.


## What each probe established, in its own output

  FreshThreadKeyboardStateReflectsLiveModifiers
      A thread that has never pumped input read `GetKeyboardState` byte 0x81 for a Left Shift held
      only by injection, while the calling thread read 0x00. So `InitThread`'s seed does see live
      state, and the cache's launch-time state is not blind. Identical on both architectures.

  ReconcileDoesNotRaceItsOwnInjectedRestorePress
      See above. 0 races, 0 stale reads, in every trial that ran.

  DwExtraInfoSurvivesSendInputWhereTheScanCodeDoesNot
      All four injected events arrived at the hook carrying `extra=0x4B4D0000` intact -- so
      `dwExtraInfo` is usable as a provenance signal. And the Right Shift leg arrived as
      `vk=0xA1 scan=0x36`: `do_keybd_event`'s rewrite to SCANCODE_RSHIFT has erased the Keyman scan
      flag, exactly the hole the tag arm exists to cover. Identical on both architectures.

  GenericShiftSendInputReflectsInBothAsyncKeyStates
      A third party's `SendInput(wVk=VK_SHIFT, wScan=0)` reached the hook already re-chiralised
      (`vk=0xA0`), and `GetAsyncKeyState` reported it for both the generic VK (0x8000) and
      VK_LSHIFT (0x8001), VK_RSHIFT clear. So a live-state reader that checks only the six chiral
      VKs is not blind to a generic injection. Identical on both architectures.


## Notes for whoever runs this next

  - It takes about four minutes per architecture, almost all of it the race probe. That is expected
    and is the reason this is not a CI target.
  - Do not type during the run. It injects real Shift keystrokes into the operator's desktop.
  - A red is not a regression until it survives a re-run in isolation:
        keyman32.interactive.tests.exe --gtest_filter=KEYBD_SHIFT.<name>
    All four have been seen going red together on one run and passing individually straight
    afterwards (2026-08-27).
  - ARM64 has no leg here, for the same reason `test:arm64` has none -- no agents, #15065. Carried
    forward as unverified in IN-TREE.md.

### And a correction to how the cost figure above should be read

The x64 depth-32 line is **126 us/event** — against 46667 us/event for the same depth, on the same
architecture, on the same machine, twenty minutes earlier. Three orders of magnitude, and it let that
depth complete its full 100 trials inside the budget where the earlier run managed 63.

So the earlier statement that `SendInput` "costs about 0.1 seconds per event through the hook chain"
is **not a property of this machine**. It is a property of what the hook chain happened to be doing
at the time, and the spread on one machine within one session is 126 us to 127548 us. Read every
figure here as an upper bound under load and nothing more. Two things follow:

  - The trial counts are the honest measure of each run's strength, which is why they are printed
    rather than assumed, and why the test is budget-bound rather than asking for a fixed count it
    cannot always reach.
  - Anyone tempted to derive an engine cost model from these numbers should not. What they establish
    is the ORACLE result -- SendInput does not return before the injected press is visible -- and
    that the fixed-count form of this test was unrunnable on a loaded machine. Nothing more.
